# Журнал участника

То, что видит команда, в JSONL-файлах по дням. Один и тот же формат пишет сервер
(`server_integrated.py`, реальные смены) и генератор недельного лога
(`generate_week_logs.py`, виртуальный купол). Журнал предназначен для RAG агента: по нему
агент учится узнавать ситуации («что было в прошлый раз при таких показаниях и чем кончилось»).

В журнале только данные, доступные ключу команды: телеметрия после фильтра политики
доступа (`authorization/access_policy.json`), с подменами показаний, заморозками и обрывами
связи, как их видел агент. Истинного состояния, названий кризисов и отчётов организаторов
в журнале нет — причину нужно выводить из данных.

## Каталог

```
<root>/
  2026-10-12/
    telemetry.jsonl   снимок телеметрии всех узлов (по умолчанию раз в 60 с)
    events.jsonl      события по времени: изменения состояний, журнал ПЛК, команды, сообщения
    logbook.jsonl     бортовой журнал жильцов (только в сгенерированном логе)
  2026-10-13/
  ...
```

Сервер пишет в `logs/participant` (переменная `DOME_PARTICIPANT_LOG`; `off` — не писать),
период снимков — `DOME_PARTICIPANT_LOG_SNAPSHOT_S`. День файла — по локальной дате сервера.

## Записи

У каждой записи: `ts` — время (ISO 8601, локальное), `kind` — тип, `dome` — часы купола
`{"day": N, "time": "HH:MM"}` (в сгенерированном логе совпадают с `ts`; на сервере в
гибридном режиме сутки купола — 3 часа).

| kind | Поля | Что это |
|---|---|---|
| `telemetry` | `nodes` | Снимок всех узлов, как в сообщении `telemetry` сервера |
| `change` | `node_id`, `param`, `from`, `to`, `note`? | Изменение дискретного поля: состояние, флаг, режим, код ошибки, `hold_reason`, `lines[i].state`, `interlocks.IL_*.state`... `note: "показание пропало"` — числовое значение стало `null` (держалось ≥ 5 опросов) |
| `automation` | `node_id`, `event`, `updated`? | Новая запись журнала автоматики купола (`dome_automation_01.events`): срабатывание интерлока (`TRIP`), действие (`ACTION`), снятие (`CLEAR`). `updated: true` — запись изменилась (квитирование) |
| `journal` | `node_id`, `param`, `entry` | Новая запись других журналов узлов (проходы через двери `access_control_01.passage_events`) |
| `action` | `actor`, `team`?, `node_id`, `action`, `value`, `success`, `error`? | Команда: `actor: "agent"` — с ключом команды (агент или люди команды через API), `"operator"` — физическое действие Оператора в куполе (осмотр кабеля, чистка фильтра, замена вентилятора, дверь бокса, режим рабочего места). `success` — ответ API: он **не гарантирует** результат (тихий дроп команд), результат виден в следующих `change`/`telemetry` |
| `message` | `sender`, `to`, `text` | Сообщение песочницы `meeting_01` (задания и просьбы Оператора, ответы агента) |
| `logbook` | `author`, `role`, `text` | Запись бортового журнала: жилец в конце рабочего дня пишет, как прошёл день и почему так вышло — **по его мнению** |

Числовые показания (ток, температура, SOC...) меняются каждый тик и есть только в снимках
`telemetry`. Штатные частые переключения (обороты/вентилятор инвертора ON↔OFF, приём радио,
двери OPEN↔CLOSED, направление ветра по сторонам света) в `change` не пишутся — их видно в снимках;
выход за штатные значения (`FAULT`, `FORCED`...) пишется.
