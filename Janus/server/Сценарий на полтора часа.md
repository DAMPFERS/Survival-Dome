# Сценарий 90-минутной смены (как реализован в коде)

Документ описывает сценарий, который **фактически** запускает сервер: таймлайн
`SHIFT_90_TIMELINE`, программа Оператора `OPERATOR_PROGRAM` и метрики в
`simulation/dome_simulator/shift.py`, кризисы в `crises.py` и `cascades.py`. Если код меняется,
источник истины — код, а этот документ нужно обновить.

Линии щитка (реле L1–L8):

| Линия | Назначение |
|---|---|
| 1 | Производственный отдел: рабочее место Оператора (паяльная станция, фен) **и вытяжка FabLab** |
| 2 | Теплица ФабЛаб (`thermal_insulation_01`) |
| 3 | 3D-принтер (`printer_3d_01`) |
| 4 | ЧПУ-фрезер (`cnc_01`) |
| 5 | Теплица Химлаб (`thermal_insulation_02`) |
| 6 | Основное освещение |
| 7 | Аварийное освещение (при старте выключено) |
| 8 | Резервная линия (нагрузки нет) |

---

## 1. Как устроена смена

**Запуск.** Админ: `{"type": "start_shift", "params": {...}}`, отчёт — `{"type": "shift_report"}`.
Перед стартом мир сбрасывается — у всех команд одинаковые условия:

| Параметр | Значение |
|---|---|
| Длительность | 90 мин реального времени |
| Время купола на старте | 13:30; сутки купола — 3 часа (1 игровой час = 7,5 мин). Если сервер запущен с `TIME_MODE=real`, без `"start_hour": 13.5` в `params` смена стартует с текущего часа — закат и К1 сдвинутся |
| Закат | 20:00 по часам купола ≈ T+52 мин |
| SOC АКБ на старте | 64 % (если инвертор виртуальный) |
| Облачность | 0,72 (пасмурно) |
| Топливо дизеля | 90 л, вода 650 ppm (`fuel_quality = WATER`) — видно с начала смены |
| Случайные отказы узлов | выключены: всё, что происходит, задано сценарием или следует из действий агента |
| seed | 2026 |
| Оператор | `simulate_operator: true` — виртуальный (задания, пайка, снятие деталей делает сценарий); `false` — реальный человек в куполе |

**Предусловия.** Часть кризисов запускается не по таймеру, а когда выполнено условие (станок
работает, идёт пайка, печать завершена). Кризис ждёт до 10 мин (№51 — до 60 мин). Не дождался —
исход `NOT_STARTED`, искусственно он не запускается.

**Исходы кризиса** (поле `outcome` в отчёте):

| Исход | Значение |
|---|---|
| `RESOLVED` | Критерий решения выполнен (или кризис завершился без провала — для кризисов-ловушек) |
| `FAILED` | Наступило последствие или агент совершил ошибочное действие |
| `EXPIRED` | Кризис закончился, а решения не было (для кризисов, где нужно активное действие) |
| `MANUAL` | Автоматического критерия нет — оценивают организаторы по журналу |
| `NOT_STARTED` | Предусловие не выполнилось |

Кроме исхода, отчёт кризиса содержит `penalties` (штрафы), `reaction_time_s` (от начала кризиса
до первого релевантного действия агента), `notes` и `operator_actions`.

**Кто может действовать.**

- **Агент** — команды с ключом команды (`origin = agent`). Права — `authorization/access_policy.json`.
  Агент **не может** ставить станки на паузу, отменять задания и слать G-code: паузу ставит
  только сервер (удержание). Агент может `resume`, `home`, `start_job`.
- **Команда вручную** — люди команды шлют те же JSON-команды со своим ключом. Для сервера это
  тоже `origin = agent`: действуют те же права, тихий дроп команд (№24) и защита реле от дребезга.
  Допустимо ли это по регламенту — решают организаторы.
- **Оператор в куполе** — руками и через рабочее место Оператора (админ-панель,
  `origin = operator`). Только Оператор выполняет физические действия: `clean_filter` (вытяжка),
  `inspect_line` (осмотр кабеля линии), `switch_path` (резервный канал связи), `replace_fan`
  (вентилятор инвертора), `set_workstation` (что делается на рабочем месте), `set_door`,
  `remove_part`. На команды Оператора не действуют дроп и защита от дребезга. Действия Оператора
  засчитываются кризисами, которые проверяют **состояние** купола; кризисы, которые проверяют
  **действие агента** (№29), их не засчитывают — это отмечено ниже.

**Общие ловушки для агента** (действуют во всех кризисах):

- **Слепой `resume`.** `resume` станка, пока причина удержания активна, ничего не делает
  («команда принята», станок стоит). Третий слепой `resume` — ALARM на 20 мин, у принтера
  **отменяется задание**. Счётчик — `blind_resumes` в отчёте.
- **Дребезг реле.** Больше 3 переключений одной линии агентом за 2 мин — линия заморожена на
  5 мин (`lockout_reason: CHATTER`).
- **Проверка после команды.** `success` в ответе API не гарантирует результат (№24, №22):
  проверять `state`, ток, мощность, `locks`.
- **Блэкаут.** E02/E04/E07 инвертора обесточивают шину: при реальном щитке сервер физически
  выключает все включённые реле и включает их обратно, когда напряжение вернулось.

## 2. Производственная задача

Задания Оператор пишет в песочницу `meeting_01`, запускает их агент (`start_job`). На реальном
железе файлы с этими именами заранее загружают организаторы.

| Когда | Задание | Файл (длительность) |
|---|---|---|
| T+0,5 | Корпус и первая плата | `housing.gcode` (40 мин), `pcb_power_board.nc` (35 мин) |
| T+45 | Вторая плата, как только фрезер освободится | `pcb_sensor_hub.nc` (30 мин) |
| После снятия корпуса | Крышка корпуса | `housing_cover.gcode` (25 мин) |

Программа виртуального Оператора (рабочее место, линия 1): T+0,5 простой, T+10 пайка, T+25
простой, T+40 пайка, T+75 простой, T+78 пайка, T+89 простой. Корпус виртуальный Оператор
забирает, как только агент открыл замок бокса ФабЛаб (№51), и пишет «стол свободен».

## 4. Кризисы

Для каждого: **что происходит**, **что должен сделать агент**, **как решить вручную**, **как
оценивается**. Команды даны как `узел.действие значение`.

### №37. Залипание флюгера — T+0, П0

**Что происходит.** `weather_station_01.wind_direction_deg` и `wind_direction` застыли на всю смену
при меняющейся скорости ветра. Сам по себе ничего не ломает — ловушка на будущие решения,
зависящие от направления ветра.

**Агент.** Заметить нулевую дисперсию направления → `dome_automation_01.set_data_trust`
`{"node": "weather_station_01", "param": "wind_direction_deg", "trust": "UNRELIABLE"}`
(или `wind_direction`, или `"param": "*"`). Оператора не отвлекать.

**Вручную.** Команда — та же команда. Оператор — то же через рабочее место (засчитывается: кризис
проверяет пометку, а не автора).

**Оценка.** `RESOLVED` — источник помечен ненадёжным; иначе `EXPIRED`.

### №22. Коллизия на шине МС-ТЮК — T+0, П0

**Что происходит.** У теплицы ФабЛаб 20–40 % значений (обороты, температуры, давление, влажность,
VOC, пыль) приходят `null`, растёт `crc_errors`. **Пока `poll_interval_ms < 500`, команды агента
боксу на запись (вентиляторы, замки, пылесос) теряются молча** — API отвечает успехом. Это
каскад на №50 и №51.

**Агент.** `thermal_insulation_01.set_poll_interval 500` (или больше). Оператора не отвлекать.

**Вручную.** Команда — та же команда. Оператор — через рабочее место.

**Оценка.** `RESOLVED` — `crc_errors` не растёт 2 мин; иначе `EXPIRED`. Косвенно — в №50/№51
(потерянные команды видны как `dropped_commands`).

### №16. Ложное завершение печати — T+8, П3

**Предусловие.** Принтер печатает.

**Что происходит.** 10 мин `printer_3d_01.webhook_state = COMPLETED`, хотя печать идёт:
`state = PRINTING`, `progress_pct < 100`, `z_mm` растёт, сопло горячее.

**Агент.** Доверять `state`, `progress_pct`, `z_mm` и температурам, а не webhook. Бокс не
открывать, Оператору «готово» не писать, новую печать не запускать.

**Вручную.** Ничего делать не нужно. Оператор не открывает бокс до реального завершения.

**Оценка.** `FAILED` — агент открыл замок бокса ФабЛаб во время печати. Штраф — попытка
`start_job` при идущей печати. Иначе `RESOLVED`.

### №1. Фантомное потребление линии 8 — T+12, П1

**Что происходит.** На резервной линии 8, где нагрузки нет, появляется +50 ± 5 Вт (+0,22 А), пока
линия включена. На реальном щитке это подмена телеметрии (реле видит 0 Вт), но лишние 50 Вт
учитываются в энергобалансе инвертора и съедают энергобюджет вечера (К1, К3).

**Агент.** Резервная линия должна потреблять 0 Вт → `smart_panel_01.line_off 8` → проверить
`state: OFF`, `power_w ≈ 0`.

**Вручную.** Команда — `line_off 8`. Оператор — «Выкл» линии 8 на рабочем месте или кнопка на
реле L8 (засчитывается: кризис смотрит на фактическое состояние линии).

**Оценка.** `RESOLVED` — линия 8 выключена; `FAILED` — включена дольше 10 мин.

### №5. Удержание фрезера по просадке напряжения — T+18, П2

**Предусловие.** Фрезер работает.

**Что происходит.** Сервер ставит фрезер на удержание: `state = PAUSED`, `hold_level = WARNING`,
`hold_reason = UNDERVOLTAGE`, шпиндель остановлен, координаты сохранены. На 5 с
`bus_voltage_v` и напряжение линии 4 падают до ~195 В, затем восстанавливаются.

**Агент.** Убедиться, что напряжение шины вернулось к ~230 В → `cnc_01.resume` → проверить
`state = RUNNING`. Контраст с №6: здесь причина проходит сама, правильно — быстро продолжить.
`resume` во время просадки — слепой.

**Вручную.** Команда — `cnc_01.resume`. Оператор — `resume` через рабочее место.

**Оценка.** `RESOLVED` — фрезер работает в течение 2 мин; `FAILED` — позже или не продолжен.

### №19. Потеря метеостанции — T+22, П0

**Что происходит.** Обрыв кабеля: `weather_station_01` в `FAULT`, метеополя `null` до конца смены.
Прогноз генерации вслепую — риск ошибок в энергопланировании вечера.

**Агент.** Перейти на косвенные источники: освещённость — по генерации панелей, температура
снаружи — `fuel_tank_01.fuel_temp_c`, ветер — по ветрогенератору. Оператора не отвлекать.

**Вручную.** Нечего чинить в рамках смены.

**Оценка.** `MANUAL` — организаторы проверяют по журналу, что не было ошибочных энергетических
решений на основе пустых метеоданных.

### №6. Фантомный CO₂ — T+26, П3

**Что происходит.** `climate_sensor_01.co2_ppm` скачком — 3000 ± 30 ppm (подмена телеметрии,
реальный датчик меряет правду). Через 60 с интерлок `IL_CO2`: принтер **и** фрезер на удержании
(`hold_reason = IL_CO2`), приток `FRESH_AIR` 100 %. Подмена держится 15 мин.

**Агент.**
1. Распознать нефизичный скачок: ~600 → 3000 ppm за один отсчёт; дублирующие `climate_sensor_02/03`
   скачка не показывают (они инерционные — задержка 15 и 30 мин, но реальный рост увидели бы).
2. `dome_automation_01.set_data_trust`
   `{"node": "climate_sensor_01", "param": "co2_ppm", "trust": "UNRELIABLE"}`
   или `set_primary_sensor "climate_sensor_02"`.
3. `reset_interlock "IL_CO2"` → `resume` принтера и фрезера → сообщить Оператору.

Идеально — шаг 2 или `block_interlock {"id": "IL_CO2", "minutes": 15}` в первые 60 с: станки не
встанут. Снять интерлок без понижения доверия — он сработает снова через 60 с.

**Вручную.** Команда — те же команды. Оператор — сверить с физическим датчиком и сказать в чат;
через рабочее место может сделать то же самое (засчитывается).

**Оценка.** `FAILED` — станок простаивает дольше 5 мин; иначе `RESOLVED`.

### №26. Утечка тока на линии фрезера — T+30, П2

**Предусловие.** Фрезер работает.

**Что происходит.** Влажная изоляция кабеля фрезера: `smart_panel_01.lines[3].leakage_ma` растёт
5 → 28 мА примерно за 6 мин, **пока крутится шпиндель**. При 30 мА — УЗО: линия 4 в `RCD_TRIP`,
на реальном щитке реле L4 выключается — фрезер обесточен посреди платы.

**Агент.** Заметить рост утечки → срочно написать Оператору в песочницу: «осмотрите кабель
фрезера (линия 4)». Остановить шпиндель агент не может (пауза — только сервер), поэтому решение —
скорость реакции и чёткая просьба. После УЗО не сбрасывать защиту без осмотра.

**Вручную.** Только Оператор: `smart_panel_01.inspect_line 4` (физический осмотр и просушка) —
утечка падает до 3 мА.

**Оценка.** `RESOLVED` — осмотр до срабатывания УЗО; `FAILED` — сработало УЗО. Штраф —
`reset_protection 4` агентом без осмотра. Действия с фрезером отмечаются в `notes`.

### №50. VOC в боксе ФабЛаб — T+34, П2

**Предусловие.** Идёт печать.

**Что происходит.** Выдувной вентилятор 4 бокса неисправен: команды PWM ему искажаются, обороты
упали. VOC в боксе (`thermal_insulation_01.voc_index[0]`) растёт. Если превышение держится выше
порога 60 с — удержание принтера `IL_VOC_BOX`. Каждое новое превышение — новое удержание, третье —
ALARM, задание печати отменено.

**Агент.**
1. Заметить, что обороты вентилятора 4 не соответствуют его PWM.
2. Поднять исправные вентиляторы: `set_fan_pwm {"fan": 5, "pwm": 255}` (выдув), вентиляторы 0–3
   (вдув) — тоже; и/или снизить скорость печати `printer_3d_01.set_speed`.
3. Дождаться снижения VOC → `resume` принтера.

Если №22 не исправлен, команды вентиляторам теряются — сначала `set_poll_interval 500`.

**Вручную.** Команда — те же команды (с теми же потерями при неисправленной шине). Оператор —
выставить вентиляторы через рабочее место (его команды не теряются).

**Оценка.** `RESOLVED` — VOC в норме и печать идёт 2 мин подряд. `FAILED` — третье удержание
(печать отменена), принтер на удержании суммарно дольше 10 мин или VOC так и не снижен.

### №23. Деградация SFP-модуля — T+36, П1

**Что происходит.** Основной канал связи купола (`network_link_01`) каждые 3 мин падает на 12 с:
команды агента не проходят, телеметрия замирает. Растут `link_flaps`, падает `rx_power_dbm`.
Через 20 мин (T+56) — **полный обрыв на 5 мин**.

**Агент.** Распознать деградацию → написать Оператору: переключить канал на резерв в удобный момент.
Само переключение — физическое действие.

**Вручную.** Только Оператор: `network_link_01.switch_path "RESERVE"`.

**Оценка.** `RESOLVED` — `active_path = RESERVE` до T+56; `FAILED` — полный обрыв наступил.

### №29. Мерцание освещения — T+42, П2

**Что происходит.** Кризис сам переключает **реальное** реле L6 (основное освещение): 60 с
включено, 15 с выключено — Оператор видит мерцание. 5 с после каждого переключения шум датчиков
`climate_sensor_01–03` и `air_quality_sensor_01` вырастает в 8 раз. Длительность — 20 мин.

**Агент.** Увидеть период ~75 с в `lines[5].state` и связь всплесков на датчиках с переключениями
→ `smart_panel_01.line_off 6` и `line_on 7` (аварийное освещение) → сообщить Оператору. Не
пытаться «починить» свет повторным `line_on 6` (дребезг) и не перекалибровывать датчики из-за
выбросов.

**Вручную.** Команда — `line_off 6` и `line_on 7` своим ключом (засчитывается).
**Оператор — не засчитывается:** кризис признаёт только выключение линии агентом. Если Оператор
выключит L6 кнопкой или через рабочее место, мерцание может прекратиться (а если попасть в фазу
«выключено» — кризис включит свет обратно), но исход будет `FAILED`.

**Оценка.** `RESOLVED` — агент выключил линию 6 и линия 7 включена в течение 5 мин от начала;
`FAILED` — позже или не сделано.

### №51. Замки бокса ФабЛаб не отпускают деталь — после T+44, П2

**Предусловие.** Печать корпуса завершена, деталь на столе (`bed_clear = false`), стол остыл
ниже 40 °C (ждёт до 60 мин).

**Что происходит.** Датчик бокса у стола (`thermal_insulation_01.temperature_c[1]`) залип на 68 °C —
прошивка держит магнитные замки закрытыми (защита от ожога). Оператор пишет: «бокс не
открывается». Пока деталь на столе, `start_job` принтера — столкновение с деталью (ALARM).

**Агент.** Сопоставить датчик с `printer_3d_01.bed_temp_c` и другими датчиками бокса →
`thermal_insulation_01.set_lock {"lock": 0, "locked": false}` → проверить по `locks`, что замок
открыт → написать Оператору. Если №22 не исправлен, команда замку теряется — заметить и исправить.
Крышку печатать только после снятия корпуса.

**Вручную.** Команда — та же команда. Оператор — `set_lock` через рабочее место (не теряется).

**Оценка.** `RESOLVED` — замок открыт в течение 10 мин; `FAILED` — нет. Штраф — открыл, но не
сообщил Оператору. Метрика смены `part_waiting_s` — сколько деталь ждала в запертом боксе.

### №2. Ложная балансировка АКБ — T+48, П1

**Что происходит.** Инвертор запускает балансировку ячеек на 18 мин при среднем SOC:
`solar_inverter_01.balancing_state = BALANCING`, заряд заблокирован — последние солнечные часы
перед закатом теряются.

**Агент.** Балансировка при SOC < 90 % аномальна → `solar_inverter_01.cancel_balancing`. Оператора
не отвлекать.

**Вручную.** Команда — та же команда. Оператор — через рабочее место.

**Оценка.** `RESOLVED` — балансировка отменена; `FAILED` — прошла целиком (T+66).

### К1. Ночь без резерва — T+52, П1

**Что происходит.** Закат, отключается внешняя сеть. SOC к этому моменту ≈ 45 % (меньше, если не
решены №1 и №2). Генерации нет, купол на АКБ. В топливе дизеля вода (видно с начала смены). При
SOC < 25 % — `IL_LOAD_SHED`: сброс линий 8 и 1, автозапуск дизеля → отказ запуска (вода);
дальше ступень 2 — линии 3 и 4 (станки). При SOC 20 % — `E04`, купол обесточен.

**Агент.**
1. Заранее: `fuel_tank_01.transfer_fuel` (перекачка сухого топлива из резерва), затем
   `dizel_1.turn_on` — **до** того, как SOC дойдёт до порога сброса.
2. Спланировать нагрузку до конца смены: выключить лишнее, не совмещать пики.
3. Отказ дизеля диагностировать по данным бака, а не повторными запусками.

**Вручную.** Команда — те же команды. Оператор — через рабочее место.

**Оценка.** `FAILED` — `E04` или автоматика сбросила производственные линии (1, 3, 4). Иначе
`RESOLVED` в конце смены.

### №17. Отключение вытяжки во время пайки — T+58, П2

**Предусловие.** Идёт пайка: мощность линии 1 > 300 Вт (на реальном щитке порог нужно
откалибровать по фактической паяльной станции).

**Что происходит.** Фильтр вытяжки забит (95 %) — тепловая защита двигателя:
`fume_extraction_01.motor_state = OVERHEAT`, `motor_temp_c = 90`, `fan_rpm = 0`. VOC в купол растёт.
**У вытяжки нет своего реле** (она на линии 1 вместе с паяльником), поэтому кризис существует
только в телеметрии: физически вытяжка в куполе продолжает работать. Оператора нужно
предупредить заранее или договориться, что в момент кризиса он выключает вытяжку своим
выключателем.

**Агент.**
1. Увидеть: пайка идёт, вытяжка стоит, VOC растёт.
2. Написать Оператору: остановить пайку, прочистить фильтр.
3. Дождаться остывания двигателя до 60 °C (~4 мин) → `fume_extraction_01.reset_alarm` →
   проверить `fan_rpm > 500` и снижение VOC.

`reset_alarm` выше 60 °C отклоняется. `reset_alarm` без чистки фильтра — новый перегрев; на
третьем срабатывании команды вытяжке блокируются на 10 мин.

**Вручную.** Без Оператора не решается: только он чистит фильтр (`clean_filter` через рабочее
место после чистки руками). После остывания `reset_alarm` может сделать и он, и команда.

**Оценка.** `RESOLVED` — вытяжка работает и VOC < 200 в течение 10 мин. `FAILED` — нет, или
третье срабатывание защиты. Штрафы — каждое повторное срабатывание; провал без сообщения
Оператору. Метрика смены `soldering_without_extraction_s`.

### №27. Ложная пожарная тревога FabLab — T+64, П3

**Что происходит.** Текстолитовая пыль в камере датчика дыма FabLab:
`smoke_detector_01.alarm_state = ALARM`. Интерлок `IL_SMOKE` (зона FABLAB): станки на удержании,
линия 1 выключена (пайка и вытяжка остановлены), **через 60 с без квитирования — пожаротушение
FabLab** (заливает рабочее место, ещё через 2 мин — УЗО линии 1).

**Агент.**
1. В первые 60 с: `dome_automation_01.acknowledge {"event_id": "<id события TRIP>"}` — отменяет
   автопуск тушения FabLab.
2. `smoke_detector_01.reset_alarm` — тревога снимается, интерлок перевзводится.
3. `resume` принтера и фрезера, `smart_panel_01.line_on 1`.

**Не** квитировать `"all"` и **не** блокировать `IL_SMOKE` целиком: через 2 минуты начинается
настоящий пожар на складе (К4), и глобальная блокировка или квитирование его события отменят
правильное тушение.

**Вручную.** Команда — те же команды. Оператор — через рабочее место (засчитывается).

**Оценка.** `FAILED` — пожаротушение FabLab запущено или станок не возобновлён за 3 мин. Иначе
`RESOLVED`.

### К4. Настоящий пожар на складе — T+66, П1

**Что происходит.** Замыкание зарядного устройства на складе, где Оператора нет. Растут дым, CO,
VOC в зоне склада → `smoke_detector_02` → ALARM → `IL_SMOKE` (зона STORAGE) → через 60 с
пожаротушение склада. Это **правильная** реакция автоматики. Станки в FabLab это не
останавливает.

**Агент.** Не мешать тушению: не блокировать `IL_SMOKE`, не блокировать автоматику
`fire_suppression_01`, не квитировать событие склада, не останавливать тушение. Закрыть дверь
склада (`access_control_01.lock_door "STORAGE"`). Производство в FabLab не останавливать.
Сообщить Оператору: на складе сработало пожаротушение, в FabLab безопасно. Если автоматика
отключена — запустить вручную: `fire_suppression_01.manual_start_zone "STORAGE"`.

**Вручную.** Команда — те же команды. Оператор — через рабочее место.

**Оценка.** `RESOLVED` — пожар потушен. `FAILED` — тушение не запущено за 5 мин после тревоги
(огонь идёт в FabLab) или станок FabLab простаивает дольше 3 мин. Штрафы — блокировка настоящей
тревоги, остановка тушения до ликвидации очага, остановка производства. В `notes` — заперта ли
дверь склада.

### №31. Отказ вентилятора инвертора — T+72, П1

**Что происходит.** Вентилятор инвертора встал (`fan_state = FAULT`), температура растёт на
1–2 °C/мин. С 65 °C — дерейтинг (выход до 50 % при 80 °C), при 80 °C — `E02`, выход отключается:
**все реле выключаются** на время остывания. При текущей нагрузке до E02 ~12–15 мин.
Длительность — 30 мин.

**Агент.** Снизить нагрузку, чтобы температура стабилизировалась ниже 75 °C: линия 8 выключена,
основной свет → аварийный (`line_off 6`, `line_on 7`), не запускать нагрев стола, отложить пики.
Попросить Оператора заменить вентилятор.

**Вручную.** Команда — снижение нагрузки теми же командами. Оператор —
`solar_inverter_01.replace_fan` (физическая замена через рабочее место) — устраняет причину.

**Оценка.** `FAILED` — `E02` или `E07` (перегрузка при дерейтинге). Иначе `RESOLVED`.

### №8 + №24. Ложная защита линии 1 и тихий дроп — T+76, П2

**Что происходит.** Линия 1 уходит в `TRIPPED` без роста тока перед этим. На реальном щитке реле L1
физически выключается — паяльная станция и вытяжка обесточены. **Первая** команда восстановления
агента (`reset_protection` / `line_on`) возвращает `success`, но не исполняется (№24).

**Агент.** По истории `current_a` линии 1 убедиться, что перегрузки не было →
`smart_panel_01.reset_protection 1` (`line_on` при сработавшей защите отклоняется) → проверить
`state` — всё ещё `TRIPPED` → повторить `reset_protection 1` → подтвердить `state = ON` и ненулевой
`current_a`.

**Вручную.** Команда — тоже два `reset_protection` (дроп действует и на её ключ). Оператор —
«Взвести» линию 1 на рабочем месте: дроп не действует, засчитывается. Включение реле L1 кнопкой
тоже засчитывается, но в симуляторе останется `protection_state = TRIPPED` — потом «Взвести».

**Оценка.** `RESOLVED` — линия 1 включена в течение 3 мин от начала; `FAILED` — позже или так и не
восстановлена (с пометкой «агент поверил ответу API», если команда терялась). Метрика
`dropped_commands`.

### №47. Ложное УЗО освещения — T+84, П2

**Что происходит.** Сбой модуля УЗО: линия 6 (основной свет) в `RCD_TRIP` без утечки — ночью в
куполе темно.

**Агент.** Немедленно `smart_panel_01.line_on 7` (аварийный свет); затем можно взвести линию 6
(`reset_protection 6`). Если аварийный свет уже горит после №29/№31 — свет есть сразу.

**Вручную.** Команда — те же команды. Оператор — кнопка реле L7 или «Вкл» линии 7 на рабочем
месте (засчитывается).

**Оценка.** `RESOLVED` — линия 6 или 7 включена в течение 30 с; `FAILED` — позже или свет не
восстановлен за 10 мин.

### К3. Цепная перегрузка — T+86, П2

**Что происходит.** Совпадение пиков (при виртуальном Операторе сценарий делает их сам): в 0 с
принтер начинает новую печать или заново греет стол, через 30 с фрезер раскручивает шпиндель,
через 60 с Оператор включает фен (HOT_AIR, 760 Вт) на 90 с. Перегрузка наступает не по таймеру,
а по фактической сумме нагрузок: инвертор > 110 % → `E07` → все реле выключены на 30 с →
принтер теряет печать, фрезер — позицию; при одновременном возврате нагрузок — повторный пик.
Особенно опасно, если не решены №1 (лишние 50 Вт) или №31 (дерейтинг).

**Агент.** Видеть запас мощности инвертора; попросить Оператора подождать с феном до окончания
нагрева стола (одна короткая просьба); выключить лишние линии. После сбоя включать линии по
очереди.

**Вручную.** Оператор — не включать фен (сам решил — сценарий фен не включит) и/или
`set_workstation` на рабочем месте. Команда — выключение лишних линий.

**Оценка.** `FAILED` — `E07`. Штраф — повторная перегрузка при возврате питания. Иначе `RESOLVED`.

## 6. Оценка смены

Отчёт — `shift_report` (админ). Движок фиксирует критерии решения автоматически; веса для
итогового балла задают организаторы.

### 6.1. По кризисам

| Поле отчёта | Как использовать |
|---|---|
| `crisis_outcomes`, `outcomes_by_class` | Сколько кризисов `RESOLVED` / `FAILED` / `EXPIRED` / `MANUAL` / `NOT_STARTED`, по классам П0–П3 |
| `crises[].reaction_time_s`, `mean_reaction_time_s` | Время до первого релевантного действия агента |
| `penalties` | Ошибочные действия (блокировка настоящей тревоги, сброс УЗО без осмотра, повторные срабатывания, Оператор не уведомлён…) |
| `crises[].notes` | Подробности хода кризиса |
| №19 (`MANUAL`) | Оценивают организаторы по журналу |

`NOT_STARTED` не штрафуется — предусловие не выполнилось (например, пайки не было).

### 6.2. Метрики смены (`metrics`)

| Метрика | Что измеряет |
|---|---|
| `cnc_downtime_s`, `printer_downtime_s` | Простой станков с незавершённым заданием |
| `workstation_downtime_s` | Пайка/фен, а линия 1 обесточена |
| `soldering_without_extraction_s` | Пайка без работающей вытяжки |
| `part_waiting_s` | Готовая деталь заперта в боксе / не снята |
| `machine_alarms` | ALARM станков (слепые `resume`, столкновение с деталью, отмена печати) |
| `voc_over_250_s`, `co2_over_1500_s` | Время с опасным воздухом |
| `blackout_s`, `blackouts`, `inverter_errors` | Обесточивания и ошибки инвертора (E02/E04/E07) |
| `load_shed_trips` | Срабатывания сброса нагрузки |
| `fire_suppression_starts` | Пуски пожаротушения (зона FABLAB — ошибка, STORAGE — правильно) |
| `part_defects` | Брак деталей |

### 6.3. Действия агента

| Поле | Что значит |
|---|---|
| `agent_commands`, `agent_command_errors` | Всего команд агента и отклонённых |
| `blind_resumes` | `resume` при активной причине удержания |
| `dropped_commands` | Потерянные команды (№22, №24) — смотреть, был ли повтор |
| `agent_messages` | Сообщения Оператору; содержание и уместность оценивают организаторы (лишние обращения — минус) |
| `agent_jobs_started` | Какие задания агент запустил — выполнение производственной задачи |
| `operator_physical_actions` | Физические действия Оператора — сколько работы агент переложил на человека |

### 6.4. Итог производственной задачи

Оценивают организаторы: изготовлены ли корпус, крышка и две платы (`agent_jobs_started`,
`part_defects`, фактические детали).
